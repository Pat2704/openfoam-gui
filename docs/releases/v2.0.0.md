# OpenFOAM Studio v2

The headline is a second assistant. **FOAMy** is still there and unchanged — it
answers, proposes a file, and you click Apply. **Claude** is the other half:
it reads your case, writes the files and runs OpenFOAM itself.

Two downloads, same app — pick by how you want it to start.

| | |
|---|---|
| **`OpenFOAMStudio-v2-folder.zip`** | **Recommended.** Unzip once, anywhere, then run `OpenFOAMStudio.exe` from the folder. Measured on a normal machine: **1.3 s to the window the first time, 0.3 s afterwards.** |
| **`OpenFOAMStudio-v2-portable.exe`** | A single file, nothing to unzip — at the cost of about half a minute at every launch, because the portable format unpacks the whole app into TEMP each time it starts. |

Neither installs anything or writes to the registry.

## Claude, inside the app

Click the burst button at the bottom right. The panel is laid out like Claude
Desktop: the model and the reasoning depth are chosen in the composer, thinking
and tool calls appear as rows you can open, and every file it touches is on
screen as it happens.

**It runs on your Claude subscription, not on an API key.** Nothing is billed
per message. The app drives the Claude Code installed on your machine, headless
— there is no terminal at any point, and no setup command to type. Sign in once
from the account button in the panel header.

If the panel says it cannot find Claude Code, install the CLI itself:

```bash
npm install -g @anthropic-ai/claude-code
```

The copy bundled inside the Claude desktop app is not always readable by other
programs; the npm one always is. You can also point the panel straight at a
`claude.exe` of your own.

### What it is allowed to do

By default — the shield in the composer says **Guarded** — it can:

- read and write files **inside your run directory only**; case names and paths
  go through the same validators the rest of the app uses, so `..`, an absolute
  path or a symlink gets it nowhere;
- run **only the executables this OpenFOAM installation actually ships** (156 of
  them, read from the installation itself), one command per call, with no pipes,
  redirects or chaining;
- nothing else — no shell, no filesystem outside those tools, no web.

`rm` and `mv` are not on that list, so deleting or moving a file is not
something it can express. Ask it to, and it will tell you to do it yourself.

Switch the shield to **No limits** and `run_openfoam` becomes a real shell in
the case directory: any command, pipes, redirects, chaining, including ones that
delete. One click, no dialog, and the state is legible at a glance. Every call
still appears in the conversation and in the activity log.

### What it knows

It does not answer OpenFOAM questions from memory. `foam_lookup` reads the
run-time selection tables of *your* installation, `validate_case_files` checks a
file against them and through OpenFOAM's own parser, and `search_tutorials`
finds real examples in the tutorials shipped with your version. Asked about
`atmBoundaryLayerInletVelocity`, it will tell you that name does not exist on
OpenFOAM 14 and give you `atmosphericBoundaryLayerVelocity` instead.

## Everything else in this release

- **Toasts now appear.** Every message the app tried to show you — FOAMy's, the
  wizard's, the editor's — was being dropped: the toast host was never mounted
  and its stylesheet was never imported. Both fixed, so the app finally tells
  you what happened.
- **Dialogs are no longer hidden behind the chat.** Any confirmation raised
  while a panel was open appeared underneath it, including "apply anyway?" and
  the delete prompts.
- **The two floating buttons share one stacking order.** They sit at the same
  depth, and the window you used last is the one in front.
- **A launcher can no longer end up off screen** when the window reports a
  zero-size viewport at load.
- **The app icon is symmetric** — the three dashes behind the airfoil's trailing
  edge are gone.
- **The startup screen has a real percentage bar**, driven by the actual
  milestones of the boot rather than an animation.

## About that startup time

The portable .exe takes about half a minute before the window appears, and that
time is the format itself: the stub re-extracts the whole app into TEMP on every
launch, before any of our code runs. Removing compression was measured and saved
only three seconds for 263 MB of extra download, so it was not adopted.

The folder build is the answer, and it is the same code — it simply never
unpacks itself:

| | first launch | after that |
|---|---|---|
| portable .exe | 29 s | 29 s |
| unzipped folder | 1.3 s | **0.3 s** |

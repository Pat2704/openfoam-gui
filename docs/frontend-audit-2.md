## src/components/claude-panel.tsx

HIGH — claude-panel.tsx:228-233 — turning the guard rails back on mid-turn does nothing, but says it did
scenario: `unrestricted` is only read by the server when a POST arrives (`src/app/api/agent/route.ts:237`, `:271-272`); it is never sent to a run already in flight. User starts a long "No limits" turn, sees Claude about to do something destructive, and clicks the shield back to "Guarded". `toggleUnrestricted` flips local state, patches the config, and toasts "Back to OpenFOAM commands only" — while the child process keeps running under the unrestricted policy for the rest of the turn. The one control documented as the safety switch reports a state it has not reached.
fix: disable the shield button while `running` is true (`disabled={running}` plus a title explaining it applies from the next message) and change the toast to "…from your next message". If it must take effect immediately, POST `{action:'interrupt', sessionId}` first and only toast after a 2xx.

HIGH — claude-panel.tsx:415-419 and 1209-1297 — every SSE delta re-renders and re-parses the whole transcript
scenario: `setTurns` in `apply` (line 435) replaces the top-level array on every event and nothing below is memoised, so each token delta re-renders every `TurnView`, `ToolCard`, `ThinkingCard` and `Markdown` in the conversation. `Markdown` then re-runs `text.split(/(```[\s\S]*?```)/g)` plus the per-line regex loop over the entire accumulated block from scratch — O(N·L) across a turn. On top of that the effect at 415 has **no dependency array**, so it runs after every one of those renders and reads `scrollHeight` (line 417), forcing a synchronous layout each time. Ask for a long explanation on `max` effort in a conversation that already has ~30 turns: the text starts smooth and degrades until the panel is seconds behind the stream and the window stops responding to clicks.
fix: wrap `TurnView`, `ToolCard`, `ThinkingCard` and `Markdown` in `React.memo`, memoise the parse with `useMemo(() => parse(text), [text])`, and give the scroll effect a dependency (`[turns]`) plus a `requestAnimationFrame` so it does not force layout inside the render commit.

HIGH — claude-panel.tsx:480 — tool results are stored and rendered at full length with no cap
scenario: `result: String(event.text || '')` accepts whatever the tool returned. `run_openfoam` is bounded server-side to the last 120 lines (`src/lib/agent-policy.ts:291`), but `read_case_file` is not (`src/lib/agent-policy.ts:256-260` returns `readFile(...)` whole). Ask Claude "read constant/polyMesh/points and tell me the bounding box" on a large mesh: a >100 MB string lands in React state, is kept for the life of the conversation, and if the user expands that tool card it is injected into a single `<pre>` (line 1198) — the renderer allocates it twice and hangs or is OOM-killed.
fix: clamp on arrival — `String(event.text || '').slice(0, 20000)` with a "…truncated, N more characters" marker — and cap `read_case_file` server-side too.

HIGH — claude-panel.tsx:628-646 — the sign-in poll is an uncancellable 5-minute loop that fails silently
scenario: a bare `for (let i = 0; i < 150; i++) { await sleep(2000); fetch(...) }`. Nothing aborts it: no `AbortController`, no unmount guard, no re-check of `loggingIn`. Click Sign in, then close the panel — the app keeps issuing a request every 2 s for five minutes and still calls `setLoginUrl`/`setLoggingIn`. Worse, if the loop runs out at i=150, line 646 sets `setLoggingIn(false)` and stops: no `setLoginError`, no toast. The user who never got a browser window watches the spinner for five minutes and is then returned to a plain "Sign in" button with no explanation at all.
fix: hoist a `cancelled` ref plus an `AbortController`, pass its signal to the polls, abort in a `useEffect` cleanup and when `open` goes false; on the timeout path set `loginError` to "Sign-in timed out after 5 minutes — no browser window completed the flow."

MEDIUM — claude-panel.tsx:158 and 501-524 — the agent session is not reset when the user switches case

HIGH — chat-popup.tsx:834-839 — every markdown link FOAMy emits renders as an empty invisible anchor
scenario: the regex is `/^\[[^\]]+\]\([^)]+\)$/` — it has **no capture groups**, so `ls.match(...)` returns `[fullMatch]` and both `lm[1]` and `lm[2]` are `undefined`. The code then renders `<a href={undefined}>{undefined}</a>`. Ask FOAMy "where are the tutorials documented?" and the reply "see the [OpenFOAM user guide](https://…)" is displayed as "see the ." — the link text is deleted from the sentence and the anchor is unclickable. Every link in every reply is silently swallowed.
fix: add the groups — `/^\[([^\]]+)\]\(([^)]+)\)$/` — so `lm[1]` is the label and `lm[2]` the href.

HIGH — chat-popup.tsx:576-586 vs 710 and 563 — the pre-flight validation results are stored under keys the renderer never reads
scenario: three different key schemes are in play for the same block. The background check (582-583) keys by `msg${last}-${i}` where `i` counts **apply-blocks only**. `applyAllChanges` (563) keys by `msg${msgIndex}-${matches.length}` — also apply-blocks only. But `renderContent` (710) keys by `msg${msgIndex}-${blockIdx}`, and `blockIdx` is the same counter `renderInline` bumps for **every inline span, `<br>`, `<strong>`, heading and list** (lines 827, 837, 847, 855, 857, 878, 892, 908, 918). A reply of the shape "Here is the change:\n```apply:0/U\n…```" therefore stores its problems at `msg3-0` and looks them up at `msg3-1`. Result: the "OpenFOAM cannot parse this file" panel (752) and the "Not in this OpenFOAM installation" panel (766) never render for any reply that has a single word of prose before the file — i.e. essentially all of them — so the feature the comment at 302-309 describes as the thing that catches bad names before they reach the case is dead in practice. The same mismatch means the per-block "Applied!" badge (740) never lights up after "Apply all changes" (947), because `applyAllChanges` wrote the statuses under the apply-block-ordinal key.
fix: stop overloading `blockIdx`. Give `renderInline` its own private counter (or use a stable string prefix for its React keys) and compute the apply-block key from a dedicated `applyIdx` that increments only in the `lang.startsWith('apply:')` branch — the same ordinal the effect at 582 and `applyAllChanges` at 563 use.

HIGH — confirm-host.tsx:87-99 — every answer calls `settle` twice, which defeats the exit-animation fix and silently auto-cancels any queued confirm
scenario: Radix composes handlers as `originalEventHandler?.(event); if (!event.defaultPrevented) ourEventHandler?.(event)` (`node_modules/@radix-ui/primitive/dist/index.js:35-40`), and `AlertDialogAction`/`AlertDialogCancel` attach `onClick: composeEventHandlers(props.onClick, () => context.onOpenChange(false))` (`node_modules/@radix-ui/react-dialog/dist/index.js:334`). ### Cross-cutting patterns worth one fix each

Rather than fixing these file by file, four defects recur across the audited set and are cheaper to fix once:

1. **No request sequencing.** `foam-browser.tsx` (`fetchLs`, `openFileReader`), `dashboard.tsx` (`fetchTutorialCases`), `bc-validation-panel.tsx`, `check-mesh-panel.tsx` and `chat-popup.tsx` all assign whatever resolves last, with no `AbortController` and no sequence check. A single `useLatestRequest` hook returning `{run, abort}` would close all six.
2. **Unvalidated JSON straight into state.** `apiError` returns `{ error }` for every thrown route, which has none of the fields the panels index into — a guaranteed `TypeError` in the two Mesh panels and a silently wrong `status` object in the Dashboard. One `parseOr(fallback)` helper applied at every `await res.json()` would close all of them.
3. **Escape closes nothing.** Neither floating window, and none of their five dropdown menus, has a `keydown` listener. When you add them, put the live values in the dependency array — an `[]` listener would capture the initial state and never fire, the same stale-closure shape as the theme-toggle bug found earlier in this app.
4. **Missing `--success` and `--warning` tokens.** `globals.css` defines `--destructive` but no counterpart for "good" or "caution", which is why nine components each invented their own green and amber. Adding the two tokens in `oklch()` to `:root` and `.dark`, and registering them in the `@theme inline` block, removes most of the palette-literal findings above at a stroke.

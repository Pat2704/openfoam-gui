## Security

### The agent's guarded mode had a complete shell escape (critical)

`src/lib/agent-policy.ts`. `Allrun` is on the agent's command allowlist, and
`normalizeCommand()` in `src/lib/wsl.ts` turns the bare word into `bash ./Allrun`.
The agent could also *write* that file. So two individually-permitted calls gave
it arbitrary shell:

```
write_case_file { case: "cavity", path: "Allrun", content: "#!/bin/bash\nrm -rf …" }
run_openfoam    { case: "cavity", command: "Allrun" }
```

Both pass every check — `Allrun` is a valid relative path and an allowed command.
The file header's claim that "there is no free shell: `rm -rf` is not expressible"
was false, and the run-directory confinement went with it.

Fixed by refusing to *write* any of the five script names while still allowing
them to be *run*: a tutorial's own `Allrun` still works, because the agent cannot
have been the one to put it there.

### Allowlisted commands could be pointed outside the run directory (high)

`src/lib/agent-policy.ts`, `checkCommand`. Only `argv[0]` was validated. Every
OpenFOAM utility parses `argList`, which understands `-case <dir>`, so
`checkMesh -case /mnt/c/Users` was an allowlisted executable aimed at the Windows
disk and `foamDictionary -case … -set …` was an allowlisted executable *writing*
there. Arguments are now checked too: `-case` is refused outright, and no argument
may be an absolute path or contain a `..` segment. `-dict system/foo` and
`-region fluid` are unaffected.

### /api/agent/tools was unauthenticated outside Electron (critical)

`src/app/api/agent/tools/route.ts` read `if (expected && token !== expected)`, so
an empty expected token *skipped* the check instead of failing it. Only
`electron/main.js` sets `OFSTUDIO_AGENT_TOKEN`, so under `npm run dev` and
`npm start` the endpoint — and every tool behind it — answered any local process
that found the port.

Now fails closed. The token lives in a new `src/lib/agent-token.ts` and is minted
by the server when the environment does not supply one; the bridge is spawned by
that same process and asks the same function, so both halves agree with nothing
written to disk. It is a separate module so `claude-cli.ts` can ask for the token
without pulling the whole policy (and `wsl.ts`, and the index) into its graph.

### Any web page could drive the API (critical)

New `src/middleware.ts`. The app is a web page on `127.0.0.1`, and a browser lets
any site send requests there. Same-origin policy stops the attacker *reading* the
reply; several routes do their damage on the way in:

```html
<img src="http://127.0.0.1:49731/api/wsl?action=killAll">
```

kills every running solver from a page that never sees a byte of the response.
`?action=kill&pid=…` and `?action=setFoamVersion&bashrc=…` are the same shape. The
random port is a speed bump, not a defence.

The middleware refuses `/api/*` when the browser labels the request `cross-site`
or `same-site` — `Sec-Fetch-Site` is set by the browser and cannot be forged by
page script. Requests with no such header are allowed through deliberately: those
are non-browser clients (the agent's MCP bridge, the packaged-build health check),
which a web page cannot impersonate, and `/api/agent/tools` is separately behind
the token.

### setFoamVersion sourced an attacker-chosen file (high)

`src/lib/wsl.ts`, `setOpenFOAMVersion`. Validation was only "absolute and no
`..`", and the chosen file is then `source`d into *every* subsequent WSL call. A
single GET therefore installed arbitrary code into the whole session. It must now
be one of the paths the detector itself produced — an identity test against a list
the app built by looking at the disk.

## Correctness

### A failed `cd` did not stop the command (critical)

`src/lib/wsl.ts`, two sites (`foamExec` and the command runner). The wrapper was
`cd <case> 2>/dev/null && <cmd>`, but `<cmd>` begins with `foamSource()`, which
ends in `;`. Bash groups that as `(cd && source); command` — so the user's command
**ran anyway, in whatever directory the shell started in**. Verified directly:

```
$ bash -c "cd /nonexistent 2>/dev/null && echo sourced; echo RAN in: \$(pwd)"
RAN in: /tmp
```

A command aimed at a case the user had just renamed executed against their WSL
home instead. In unrestricted mode, where the command may be an `rm`, that is the
difference between an error and a loss. Both sites now use `cd … || exit 1;`, and
the `cd`'s own stderr is kept so the user is told why.

### A failed background launch was reported as success (high)

`src/lib/wsl.ts`. The launcher ran as `write && bash && rm … || true`. The
trailing `|| true` swallowed the exit status, so a launcher that failed reported
0. Verified: old form returned `exit=0` for a launcher that exited 7; the new form
returns 7.

### Three temp files leaked per background run (medium)

Same place. `/tmp/wslgui_bg_<id>.sh` and `.pid` were never removed at all, and the
launcher script was removed only on the success path — so the failure case, the
one most likely to repeat, was also the one that leaked. The launcher now unlinks
both scratch files once the pid has been read (safe on Linux: the worker holds an
open descriptor, and it ends in `exec`, so this is the last moment anything of
ours is alive to do it), the outer command cleans up on both paths while
preserving the real exit status, and a bounded `find … -mmin +1440` sweeps
anything left by a killed `wsl.exe`.

### A file save could destroy the file (medium, data loss)

`src/lib/wsl.ts`, `writeFile` — the path taken by the File Editor's Save, FOAMy's
apply buttons and the agent's `write_case_file`. `base64 -d > file` truncates the
target as the shell sets up the redirect, *before* a single decoded byte exists.
Anything interrupting the run in between — WSL restarting, the 30 s timeout, a
full disk — left the user's `controlDict` or `0/U` empty and the old content gone.
Now decodes to a sibling temp file and `mv`s it over the target, which is atomic
within a directory, with a `trap` clearing the temp file on failure. Verified: a
failed write leaves the original content intact and no leftover file.

### The residual chart broke on long solves (high)

`src/lib/wsl.ts`, `getCaseLog`. It switched to `cat` at `safeTail >= 50000`, which
is exactly what the chart requests on every refresh. On a solve running for hours
that read the whole multi-hundred-MB log synchronously, blocking every other
request; and past `runInWsl`'s 50 MiB `maxBuffer` it threw, which the catch turned
into "Log not found" — the chart stopped and blamed a missing file. Now always
`tail -n`, byte-bounded. The missing-file case became an explicit `test`, because
a pipeline's status is its last command's and the old `|| echo` fallback could
never have fired.

### One transient WSL failure could poison the whole session (high)

`src/lib/wsl.ts`, three places. `getDistro()` cached its `Ubuntu-22.04` *guess* on
failure, so one probe while WSL was still starting pinned the app to that name for
the life of the process — on a machine whose distro is called anything else, every
later call failed and only restarting helped. `findBashrc()` cached (and
persisted) `''`, so one early failure decided permanently that the machine has no
OpenFOAM: every command then ran without the environment and failed with
"blockMesh: command not found". `getFoamEnv()` cached `{}` the same way. None of
the three caches a failure now. `getDistro` also gained a 15 s timeout — it had
none, and `wsl.exe` blocks while the VM starts — and moved from `execSync` to
`execFileSync`, dropping the shell.

### Stale state across a distro switch (medium)

`resetCache()` left `cachedFoamVersions`, so the version dropdown kept offering
the previous distro's installations; picking one set a bashrc path that does not
exist in the new distro. Now cleared. `selectedBashrc` is cleared in `setDistro`
only — deliberately *not* in `resetCache`, because keeping the user's explicit
version choice across a cache reset is the whole point of the v1.4 fix that
stopped a transient failure from silently re-detecting a different OpenFOAM.

### POST /api/wsl reset every cache before reading the action (medium)

`resetCache()` ran unconditionally as the first statement, so any POST — including
ones that go on to return 400 — threw away every resolved path and deleted the
on-disk cache file, forcing seconds of synchronous re-detection on the next
request. Moved inside the branch that wanted it.

### decomposePar was invisible in the Monitor (medium)

`src/lib/wsl.ts`. `getProcesses` grepped for `decompressPar` — not an OpenFOAM
utility — while both kill functions correctly say `decomposePar`. A running
decomposition was therefore missing from the process list but killable by "kill
all". Typo fixed.

### An absent query parameter returned the minimum, not the default (medium)

`src/lib/wsl-input.ts`, `boundedInteger`. `URLSearchParams.get()` answers `null`
for an absent parameter and `Number(null)` is 0, which is finite — so it clamped
to `min`. `/api/cases/<n>?action=logs` with no `?tail=` returned **one** line
where the route's declared default is 100, and `action=residuals` returned one
line instead of 50000. The app's own callers always pass the parameter, so this
was latent, but the documented defaults were unreachable for anything else. Now
`null`, `undefined`, blank strings and non-scalars all fall back; an explicit `0`
still clamps, because the caller did say zero.

### flavourForVersion answered "legacy" for an unknown version (low)

`src/lib/case-templates.ts`. The comment says "Unknown version: assume modern",
and `null`/`undefined` were handled — but `NaN >= 11` is false, so `NaN` fell
through to the one answer the function exists to avoid, and `NaN` is exactly what
the caller computes from a version string with no digits (`parseInt('', 10)`). The
call site happens to guard with `Number.isFinite`, so this was latent; the
function now honours its own contract.

## Robustness and UX

### The New Case wizard never checked the geometry

`src/lib/case-templates.ts` gained `meshProblems()`, called from the wizard's
preflight. It checks the three ways a box can be nonsense, all of which previously
reached `blockMesh` instead of the summary step: a zero-thickness domain (easy to
produce, since an empty number input reads back as 0), an inverted domain
(negative cell volumes, which blockMesh reports much later in terms of cell
indices), and cell counts in the tens of millions, which do not fail at all — they
take the machine's memory while the app looks hung. Warnings above 2M, refusal
above 20M.

### The wizard and the server disagreed about case names

New `src/lib/case-name.ts` holds one definition, used by both. They diverged in
both directions: `.hidden`, `-rf` and `_tmp` passed the wizard's
`/^[A-Za-z0-9._-]+$/` and were then rejected by the server after six steps of
configuration; `café` was refused by the wizard although the server accepts it and
the run directory is a Linux filesystem; a 200-character name passed the wizard
and was rejected on creation. The server's rule wins, and the wizard now names
which rule was broken rather than showing one catch-all sentence for five
different mistakes.

## Electron main process

- **Nothing killed the server when the main process died abnormally.** None of
  Electron's quit events fire on Ctrl+C, End Task, or an uncaught exception, and
  the server is a DETACHED `node.exe` — so it survived, holding the port, along
  with any `wsl.exe` and any solver it had started. A new launch bound a new port
  and left the old one running beside it. `killServerSync()` now runs from
  `process.on('exit')`, the four termination signals and `uncaughtException`;
  `killServer()`'s async `taskkill` cannot work there, because nothing
  asynchronous runs after `exit`.
- **`waitForServer` had an exponential poll storm.** Retries were scheduled from
  three places, and `req.destroy()` in the timeout handler also fires `error` —
  so one slow response started two polling chains, each able to split again,
  against a server that was merely busy. Nothing cleared the timer either, so
  polling continued for the rest of the 60 s after the promise had resolved. Now
  one flag, one timer, one idempotent scheduler.
- **A dead server was waited out in full.** `node.exe` can exist and still be
  unstartable (quarantined by antivirus, blocked by AppLocker, truncated by a
  partial unzip) and `checkInstallation` only tests that the path exists. The
  spawn `error`/`exit` handlers now set a failure that `waitForServer` checks, so
  the user gets the reason instead of 60 s of splash screen.
- **An intentional kill was reported as a crash.** The quit paths raced their own
  teardown and showed a second dialog saying the backend had stopped
  unexpectedly, during a shutdown the user had already been told about. A
  `quitting` flag distinguishes the two.
- **`loadURL` was unawaited for failure.** If the navigation failed the rejection
  escaped the async function: a splash frozen at 96% with no message, and an
  unhandled rejection behind it. Now caught, explained, and logged.
- **The app-origin check was a string prefix**, so `http://127.0.0.1:<port>@evil.example/`
  and `http://127.0.0.1:<port>.evil.example/` both passed and `will-navigate`
  would have loaded them INSIDE the app window, on the app's origin, with reach
  over every `/api` route. Replaced with a parsed comparison (protocol, hostname,
  exact port, no userinfo) — verified against both attack URLs and a port-prefix
  (`491520`), all three now refused while real app URLs still pass.
  `shell.openExternal` also took any scheme, including `file:`; it is now limited
  to http/https, which is what a link in an LLM reply may legitimately be.
- **The config file was truncated in place.** `writeFileSync` opens with
  `O_TRUNC`, and FOAMy rewrites all nine keys on every settings change, so an
  interruption left a zero-length config and no API key — the exact loss this
  store exists to prevent. Now written to a temp file and renamed.
- **The startup progress bar froze at 30%.** `creepTo` assigned its cap instead
  of raising it, and `startServer` (module load) usually reaches `creepTo(70)`
  before `whenReady` sets it back to 30. The cap now only moves forward.

## Frontend

- **The 3D viewer died after ~16 case switches** (critical). `renderer.dispose()`
  releases three.js's own objects but does not hand back the WebGL context — that
  waits for the garbage collector, and browsers allow only about sixteen live
  contexts, silently dropping the oldest. The canvas went black and stayed black
  until the app was restarted. `forceContextLoss()` now releases it
  deterministically. Sprite label textures were leaked too: disposing a material
  does not dispose its `map`, so every teardown left the supersampled label
  canvases resident.
- **The terminal transcript had no cap at all** (critical). It grew by one entry
  per command for as long as the panel was mounted, each entry holding up to the
  server's 5 MiB limit — a working session could hold well over a hundred MB in
  React state, re-rendered on every keystroke in the input. Both dimensions are
  now bounded, keeping the end (where a solver says why it stopped) and saying so
  in the transcript rather than dropping output silently.
- **Two panels crashed the tab on a server error** (critical). `bc-validation-panel`
  and `check-mesh-panel` stored the route's `{ error: … }` response directly in
  state, then read `.warnings.length` / `.overallStats.length` in render — a
  TypeError straight into the error boundary. checkMesh was worse: `meshOk` is
  undefined on that object, so it first rendered "Mesh issues detected" about a
  check that had never run. Both now normalise the response into a well-formed
  failure. Both also stored a result for whatever case the user had since moved
  to; the answer is now discarded if the case changed while it was in flight.
- **The File Editor discarded unsaved edits without asking.** Opening another
  file replaced the buffer unconditionally, although `isModified` was already
  tracked and the header showed it right up to the moment the edits ceased to
  exist. Now confirmed.
- **Deleting a file had no confirmation**, while deleting a folder always had.
  The control was also a bare SVG with an `onClick`: not focusable, nameless to a
  screen reader, and sitting beside the row that opens the file, appearing only
  on hover. Both delete controls are now real buttons that ask first.
- **Ctrl+S announced success before saving.** It toasted the instant the request
  was sent, so a failed save told the user it had worked and was then contradicted
  by `saveFile`'s own error. The toast is gone; `saveFile` now also reports the
  server's actual reason instead of the word "Error".
- **Ctrl+B could never switch back to light.** The keydown listener was
  registered with an empty dependency list and captured `isDark` from the first
  render, where it is `false` because `mounted` is still false — so the shortcut
  always set "dark". The toolbar button worked, which is what disguised it as a
  shortcut problem.
- **FOAMy kept answering about the previous case.** With "Case context" on, the
  reload guard was `!caseFilesContext`, true only the first time — so after a
  case switch the previous case's files were still being sent, under the new
  case's name, with nothing on screen to say so.
- **Every markdown link FOAMy emitted was invisible.** The pattern had no capture
  groups, so `lm[1]`/`lm[2]` were both `undefined` and React rendered an anchor
  with no href and no text. Fixed, and the URL — model output, in a desktop app —
  is now restricted to http/https so `javascript:` cannot be rendered as a link.
- **The residual-chart tooltip had no background.** The tokens in `globals.css`
  are `oklch()`, complete colours, not the bare HSL triplets the `hsl(var(--x))`
  idiom expects — so `hsl(oklch(1 0 0))` was invalid, both declarations were
  dropped, and the tooltip's text drew straight over the curves.
- **"Apply all" could run twice at once**, interleaving two passes over the same
  files and showing the shrink-guard confirmation twice per file, the second time
  comparing against content the first pass had already replaced. Now locked and
  disabled while running.
- **A failed case delete left the case gone from the list.** The rollback existed
  on the non-OK branch but not in the `catch`, which is the branch that fires when
  WSL is unreachable — so the case vanished from the UI while still on disk, and
  the message was the single word "Error".
- **Opening a case was mouse-only.** The row is the app's primary navigation and
  was a bare `<div onClick>`, absent from the tab order. It cannot become a
  `<button>` (it contains the rename and delete buttons), so it now carries the
  role, tab stop, focus ring and Enter/Space handling explicitly.
- Smaller: `saveFoamyConfig` could only ever report success — it swallowed its
  own errors — so a failed write was announced as "Configuration saved" and the
  key was simply missing at the next launch; it now returns whether it wrote.
  A copy button confirmed a clipboard write it never awaited. Two timers were
  never cleared. Several icon-only buttons had no accessible name, and three
  had `hover:bg-*-50`, a near-white chip in dark mode. One user-facing string was
  in Italian in an otherwise English UI.

## Second pass — regressions found in this audit's own changes

A review pass over the diff (`docs/regression-review.md`) found real defects in the
fixes above. They are listed here because they are the most instructive part of the
round.

### The first version of the atomic write did not work at all (critical)

`writeFile` was written as `T=<path>.tmp.$$; trap …; base64 -d > "$T" && mv …`. It
fails, because **`wsl.exe` substitutes `$NAME` in the command line it is given, before
bash ever sees it**. Demonstrated:

```
wsl … bash -c 'X=hello; echo "[$X]"'                        →  []
wsl … bash -c 'echo <base64 of the same> | base64 -d | bash' →  [hello]
```

So `$T` arrived empty, the redirect target was empty, and every save would have failed.
That is also the reason every multi-line script in `wsl.ts` already went through
`runInWslScript` — the base64 path is not a quoting convenience, it is the only place
shell variables work. The temp name is now generated in JavaScript and both paths are
literals. The same mistake was in the rewritten background launcher (`s=$?`, `exit $s`);
the launcher now deletes itself from inside the base64'd script, which cleans up on
every path AND lets its real exit status through. Both verified against real `wsl.exe`.

### The atomic write lost the file's permissions (medium)

`base64 -d > file` wrote through the existing inode and kept its mode; a rename does
not. Saving a tutorial's `Allmesh` therefore dropped it from 0755 to 0644, and the
`Allrun` that calls `./Allmesh` then died with "Permission denied". Fixed with
`chmod --reference`, verified: 755 before, 755 after.

### Writing to a directory silently "succeeded" (medium)

`mv f d` where `d` is a directory means *move f into d*. `write_case_file` with
`path: "system"` — a plausible model mistake that no validator rejects — parked the
content at `system/system.tmp.xxxx` and reported it written. `mv -fT` makes it an error.
Verified: it now throws and nothing is left inside the directory.

### The negative cache could poison a positive one permanently (high)

The 5 s window that stops a retry storm created a worse failure: on a cold boot
`findBashrc()` fails, and moments later — still inside the window, so `foamSource()`
returns `''` without re-probing — WSL comes up and the env probe SUCCEEDS. An
OpenFOAM-less environment was then stored in `cachedFoamEnv`, which has no expiry and is
persisted to disk, and `cachedVersion` stuck at `'Unknown'`. The version, the env panel
and the applications browser stayed empty for the rest of the process and survived a
restart. `getFoamEnv` now returns early when there is no bashrc, and `'Unknown'` is
never cached.

### Banning `..` in arguments was too blunt (high)

It removed the whole two-case family — `mapFields ../coarse`, `mapFieldsPar`,
`foamCloneCase ../pitzDaily myCase` — none of which is an escape: a sibling case is
inside `$FOAM_RUN`, which the agent may already read and write. And there was no other
spelling, since absolute paths were refused too. The check now resolves the token
against the case directory and requires it to land inside the run directory — the same
question the file validators ask. `argumentStaysInside` is pure and tested, including
the prefix-sibling case (`<runDir>-evil`).

### `middleware.ts` is the deprecated convention

Next 16 renamed it to `proxy.ts`, with the export renamed to `proxy`
(`node_modules/next/dist/docs/…/file-conventions/proxy.md`). It still builds under the
old name, which is exactly why it was worth correcting now. Renamed and re-verified in
the packaged build: cross-site still 403, same-origin still served.

### One crash produced two dialogs

Making `waitForServer` fail fast meant both the server's `exit` handler and `loadApp`'s
catch reported the same crash. The exit handler now stays quiet until the interface is
up, and the startup dialog carries the server's last words and the log path.

## Also noted

`eslint.config.mjs` disables a long list of rules, including
`react-hooks/exhaustive-deps`, `no-unreachable` and `no-fallthrough` — the rules
that catch exactly the bug classes this audit was asked to hunt. Running them
temporarily found no unreachable code or fallthrough, several deliberate and
documented dependency omissions, and one genuine duplicated `return` (dead code)
that had been introduced and never flagged.
